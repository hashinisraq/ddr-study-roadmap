Run a DRAM Simulator

See behavior you can't observe on real hardware: scheduling, row hits vs conflicts, and how timing changes ripple into bandwidth and latency.

Free, open-source tools

ToolGood forWhere
Ramulator 2.0Modern, flexible; supports DDR4 & DDR5github.com/CMU-SAFARI/ramulator2
DRAMSim3Cycle-accurate, widely usedgithub.com/umd-memsys/DRAMsim3
gem5Full-system: CPU + controller + DRAM togethergem5.org

What to actually do

  1. Run a streaming access pattern (sequential addresses); note the bandwidth.
  2. Run a random access pattern; note how much bandwidth drops.
  3. Explain the gap using row hits vs conflicts (Lesson 1): streaming reuses open rows (hits); random keeps opening and closing rows (conflicts).
From concept to evidence The simulator turns the abstractions of Phases 1-2 into numbers you can measure. Seeing bandwidth collapse under random access - and tracing it to row conflicts - is the moment the whole model clicks.
Check yourself
  1. Which tool would you pick to study the CPU + memory together, and why?
  2. Predict the bandwidth ordering of streaming vs random before you run it.
  3. Explain the measured gap in terms of row hits and conflicts.
